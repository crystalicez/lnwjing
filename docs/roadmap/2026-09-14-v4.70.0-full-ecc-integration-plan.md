# lnwjing v4.70.0 — Full ECC Integration Plan

Date: 2026-09-14  
Branch: `dev`  
Baseline: lnwjing `4.63.0`, commit `e4fbb8097c7776b5f409f86fc91c3366026428c7`
Target: lnwjing `4.70.0`
Upstream ECC release: `ecc-universal@2.2.1`  
AgentShield release: `ecc-agentshield@1.4.0`

## Destination

Integrate the complete ECC ecosystem into lnwjing as a managed provider without replacing lnwjing's own security, permission, durable-goal, scheduling, tool ownership, recovery, or process-control runtime.

“Complete ECC integration” means lnwjing can discover, inspect, selectively activate, and route all major ECC artifact classes:

- agents
- skills
- command shims
- common and language/domain rules
- hooks and lifecycle metadata
- native/pilot workflows
- MCP server templates
- Memory Vault semantics
- continuous-learning / instinct surfaces
- AgentShield security scanning
- provenance and upstream version metadata

The integration MUST NOT blindly inject all ECC content into every prompt, auto-run arbitrary ECC hooks, auto-enable all MCP servers, auto-promote memory into policy, or give imported artifacts authority over lnwjing's permission and durable-execution boundaries.

## Research findings / upstream contract

### ECC package and provenance

Current public release is `ecc-universal@2.2.1` (MIT). Upstream describes ECC as a harness-native engineering system around planning, testing, implementation, review, verification, memory, and improvement.

The upstream package/repository currently contains the following high-level surfaces:

- 68 agent definitions
- ~291 repository skills (the npm package surface may contain fewer depending on package filtering)
- 94 legacy command shims
- hooks + hook metadata
- layered rules
- workflows
- MCP templates
- Memory Vault CLI/MCP design
- continuous learning and instincts
- AgentShield integration

The integration must record exact package version and source provenance. Counts are informational and must be discovered dynamically from the installed package rather than hard-coded as acceptance criteria.

### Hooks

ECC hooks are event-driven and can block/warn/run post-actions. Upstream maintains stable sidecar hook IDs/fingerprints and exposes profiles such as `minimal`, `standard`, and `strict`.

lnwjing integration rule:

- import hook descriptors as data
- preserve stable ECC IDs where present
- translate only supported lifecycle events into lnwjing hook descriptors
- never execute arbitrary imported shell commands directly
- unsupported/executable hook commands remain inspectable, disabled, and security-scannable
- activation must pass lnwjing permission policy

### Rules

ECC rules are layered:

- `common/`
- language/framework/domain-specific rule directories

Specific rules override common rules upstream. lnwjing must preserve that layering in catalog metadata and load only relevant rule sets based on project profile / explicit selection. Rules are context, not a permission bypass.

### MCP templates

ECC ships a broad `mcp-configs/mcp-servers.json` template. Upstream explicitly warns to keep enabled MCP servers bounded to preserve context.

lnwjing integration rule:

- templates are discovered/imported as disabled descriptors
- credentials/placeholders are never retained as active secrets
- no ECC MCP template is auto-launched
- activation routes through lnwjing MCP Hub / child-server security
- template requirements and placeholder env vars are shown to the user

### Memory Vault

ECC Memory Vault defines human-readable Markdown memory under `.ecc/memory/` with schema `ecc.memory.v1`.

Critical trust rules to preserve:

- memory is context, not instruction
- new memory is `trust: "unreviewed"`
- writes are create-only
- no auto-promotion into rules/skills/policy
- user scope requires explicit opt-in
- known secret shapes are rejected
- symlink/path escapes fail closed
- active lexical search is bounded
- governed project docs remain authoritative

lnwjing already has durable goal/session/handoff state. ECC memory must complement, not replace, that state.

### Workflows / orchestration

ECC native workflows are currently a pilot and include multi-agent review orchestration. Interactive human gates remain outside autonomous workflow segments.

lnwjing integration rule:

- represent workflow definitions as inspectable recipes/provider workflows
- fan-out maps to owned `delegate` / `parallel_delegate`
- interactive gates remain in the main lnwjing goal/session
- durable goals remain the authoritative long-running execution state
- imported workflows cannot create their own competing scheduler/lease system

### Continuous learning / instincts

ECC continuous learning extracts reusable patterns into instincts with confidence/evidence.

lnwjing integration rule:

- imported/generated instincts are advisory context
- project scope overrides global scope only within the instinct layer
- instincts cannot auto-promote to AGENTS.md, rules, permissions, tools, or policy
- any future promotion requires an explicit governed action

### AgentShield

AgentShield scans agent configuration, hooks, MCP configs, permissions, secrets, and prompt-injection risks.

lnwjing integration rule:

- pin `ecc-agentshield@1.4.0`
- support deterministic local scan execution
- separate scanner facts from lnwjing remediation judgment
- no blind `npx -y latest` execution
- scanner output must be bounded and structured before it enters model context
- security scan must be available against imported ECC material before activation

## Architecture decision

### Provider model

Implement a first-class `ECC Provider` inside lnwjing.

The provider owns discovery and metadata, not execution authority.

```text
ECC package/resource root
        |
        v
ECC Provider / Scanner
        |
        +--> Agents catalog ---------> lnwjing delegate adapter
        +--> Skills catalog ---------> existing skill_match / skill_load
        +--> Commands ---------------> compatibility alias -> skill/recipe
        +--> Rules ------------------> layered contextual rules
        +--> Hooks ------------------> safe descriptor adapter
        +--> Workflows --------------> recipe/orchestration adapter
        +--> MCP templates ----------> MCP Hub disabled templates
        +--> Memory -----------------> ECC Memory Vault bridge
        +--> Instincts --------------> advisory learning catalog
        +--> AgentShield ------------> security scan service
        |
        v
lnwjing permission / scope / audit / durable-goal authority
```

### Import 100%, activate selectively

“Full” means catalog coverage, not universal eager activation.

Every discovered artifact receives:

- provider: `ecc`
- upstream version
- source path
- artifact type
- stable ID
- title/name
- description when available
- trust state
- activation state
- compatibility state
- optional requirements
- optional security status

The router loads/activates only what is required by the task/project.

### Runtime authority hierarchy

1. lnwjing host security / permission profile
2. durable goal ownership / lease / task ownership
3. project AGENTS.md and governed project policy
4. reviewed lnwjing configuration
5. selected ECC rules/workflows/skills
6. ECC memory and instincts as unreviewed/advisory context

ECC content may never override a higher layer.

## Proposed implementation slices

### Slice A — Provider core and provenance

Primary files expected:

- `packages/mcp-server/src/ecc-provider.ts` (new)
- `packages/mcp-server/src/ecc-types.ts` (new)
- `packages/mcp-server/src/upgrade-runtime.ts`
- `packages/mcp-server/src/upgrade-catalog.ts`
- `packages/mcp-server/src/upgrade-tool-contracts.ts`
- `packages/mcp-server/package.json` and lockfile as needed

Responsibilities:

- locate pinned bundled/package ECC root
- validate package identity/version
- scan supported artifact roots
- build bounded typed inventory
- calculate provenance/fingerprint
- expose status/catalog APIs
- never execute imported code during discovery

New MCP surfaces should be minimal and composable, likely:

- `ecc_status`
- `ecc_catalog`
- `ecc_configure`
- `ecc_security_scan`

Specialized existing tools should remain the execution surfaces when possible.

### Slice B — Agents, skills, commands, rules

Agents:

- parse frontmatter/metadata
- expose as ECC agent descriptors
- route bounded read-only specialist tasks through owned delegation
- never grant agent tools based only on ECC frontmatter

Skills:

- make ECC skills discoverable through the existing skill catalog
- avoid bulk-loading skill bodies
- preserve source-qualified IDs
- deduplicate mirrored provider-native copies where applicable

Commands:

- map legacy ECC command shims to target skill/recipe/agent when resolvable
- keep commands as compatibility aliases, not a second workflow engine

Rules:

- parse common + specific rule layers
- select by project intelligence profile and explicit configuration
- retain precedence metadata
- load only selected rule text

### Slice C — Hooks, workflows, MCP templates

Hooks:

- import stable hook IDs/metadata/fingerprints
- map safe declarative events
- keep arbitrary command hooks disabled unless a dedicated reviewed adapter exists
- expose hook profile configuration
- scan before enable

Workflows:

- catalog workflow scripts as metadata
- provide safe adapters for supported orchestration patterns
- review/fanout maps to `parallel_delegate`
- no direct evaluation of arbitrary imported JS workflow code in the privileged main process

MCP templates:

- parse server templates
- redact/flag placeholder credentials
- import disabled descriptors only
- enable through normal MCP Hub setup
- no automatic process launch

### Slice D — Memory Vault and instincts

Implement ECC Memory Vault compatibility as a bounded provider-owned service rather than invoking upstream shell CLI for normal operations.

Expected requirements:

- `ecc.memory.v1` parser/validator
- project/team scopes
- user scope disabled by default
- create-only save
- bounded lexical search
- read by ID
- doctor/diagnostics
- symlink/path fail-closed
- secret-shape rejection
- terminal-control sanitization
- no raw body logging
- no automated promotion

Bridge handoffs:

- `handoff_context` may include links/references to ECC handoff memories
- durable goal/session state remains authoritative for execution

Instinct catalog:

- discover existing ECC instinct files when present
- expose confidence/evidence as advisory metadata
- do not auto-apply or promote

### Slice E — AgentShield security

Add pinned AgentShield integration.

Preferred execution:

- package-installed reviewed binary/library
- bounded process execution through lnwjing-owned process boundary
- exact version reported
- JSON output preferred
- timeout/output cap
- no network required for deterministic scan mode
- scan imported provider root and target project separately

Acceptance:

- a malicious hook/MCP/secret fixture produces findings
- safe fixture returns expected clean/low-risk result
- scanner failure never becomes a false “clean” state

### Slice F — Desktop UX / IPC

Expose ECC integration in Settings/Tools without creating a large new navigation surface unless existing UX requires it.

Expected surfaces:

- provider installed/version/provenance
- catalog counts by artifact type
- activation mode: disabled / selective (default)
- hook profile
- selected rule sets
- Memory Vault status
- AgentShield status / scan action
- MCP template count with explicit “disabled until configured” messaging
- sync/refresh status if runtime refresh is supported

Likely files:

- `packages/ipc-contracts/**`
- `apps/desktop/src/main/desktop-services.ts`
- `apps/desktop/src/main/tool-catalog/**`
- `apps/desktop/src/preload/**`
- `apps/desktop/src/renderer/features/settings/SettingsPage.tsx`
- related settings CSS/i18n/tests

UI must make it clear that “available” is not the same as “enabled/configured”.

### Slice G — Packaging/provenance

Installer must contain enough ECC material to work after install without depending on the source checkout.

Options evaluated during implementation:

1. package dependency bundled into Electron resources
2. curated resource copy from pinned package during packaging

Preferred criteria:

- deterministic version pin
- license included
- integrity/provenance evidence
- no runtime `latest` downloads
- package updater does not silently change ECC version independently of lnwjing

Add/update:

- third-party notices
- packaging tests
- release evidence / package integrity checks as needed

## Security invariants

The following are non-negotiable acceptance gates:

- imported hook command text never executes during discovery
- imported MCP templates never auto-start
- credential placeholders never become live secrets
- imported agent tool lists do not widen lnwjing permissions
- memory/instinct content cannot become policy automatically
- no ECC artifact can bypass workspace scope
- no imported workflow can create a competing Native Scheduled Task / cron / OS scheduler
- provider discovery is bounded and symlink-safe
- provider status reports exact source/version/provenance
- scanner failure is reported as unavailable/error, never clean
- unsafe external content remains untrusted context

## Test strategy

Use the smallest sufficient checks per slice, then a broader gate before push.

### Focused unit/contract tests

Provider:

- version/provenance discovery
- typed artifact inventory
- malformed frontmatter
- duplicate IDs
- symlink/path escape behavior
- bounded reads

Adapters:

- agent permission intersection
- skill dedupe and lazy body load
- command alias mapping
- rule precedence
- hook disabled-by-default executable behavior
- MCP template placeholders
- workflow fanout mapping

Memory:

- create-only semantics
- duplicate ID refusal
- secret rejection
- active search filtering
- incomplete/malformed doctor behavior
- user scope opt-in

Security:

- AgentShield invocation contract
- bounded output/timeouts
- failure-closed state

Desktop:

- IPC schema validation
- Settings rendering
- enabled/configured distinction

Packaging:

- ECC resource/package present
- exact pinned version
- licenses/provenance included

### Verification sequence before push

1. affected tests
2. MCP server tests for new tools/provider
3. desktop focused tests
4. typecheck
5. lint
6. docs/tool catalog checks if catalog changes
7. packaging-focused tests
8. `git diff --check`
9. `review_changes` + affected modules
10. LSP diagnostics on changed source files
11. broader/full suites if affected scope warrants

### Dev CI

After commit/push:

- resolve exact GitHub Actions run ID for pushed SHA
- monitor that exact run with durable `gh run watch <RUN_ID> -i 20 --exit-status`
- inspect failed exact-run logs before any repair
- do not treat “latest dev run” as authoritative after monitoring starts

## Versioning and delivery

Only after implementation and validation:

- bump repo to `4.70.0` using existing version tooling
- update README/FULL_README/tool docs/relevant roadmap notes
- commit only intended ECC/v4.70.0 changes
- push `dev`
- wait for exact dev CI terminal green
- build fresh Windows Setup/Portable artifacts using existing packaging path
- verify artifact hashes/provenance/version
- report installer path to user for testing

Explicitly DO NOT:

- create PR
- merge `main`
- tag `v4.70.0`
- publish GitHub Release
- publish npm/package release

Those actions wait for user testing and a later explicit instruction.

3. **Content Adapters** — agents/skills/commands/rules.
4. **Runtime Adapters** — hooks/workflows/MCP templates.

6. **Security** — AgentShield and deterministic provider scan.
7. **Desktop UX** — settings/status/actions and IPC.

## Acceptance definition

The goal is complete only when all of the following are true:

- plan artifact exists and matches implemented architecture
- ECC provider discovers the pinned ECC package and major artifact classes
- selective activation works without eager prompt/context flooding
- agents/skills/commands/rules are usable through lnwjing adapters
- hooks/workflows/MCP templates are safely inspectable/configurable
- Memory Vault compatibility honors unreviewed/create-only/trust boundaries
- instinct/continuous-learning data is advisory only
- AgentShield scan is integrated and version-pinned
- desktop exposes truthful provider/configuration state
- relevant tests/typecheck/lint/diagnostics/review pass
- repo version is 4.70.0
- intended changes are committed and pushed to dev
- exact dev CI is terminal green
- fresh Windows installer artifacts are built and verified
- no PR/main/tag/release was performed
