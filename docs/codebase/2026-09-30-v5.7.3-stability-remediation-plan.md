## 2. Source-backed findings

### 2.1 AppImage startup is currently fatal when secure storage is unavailable

`apps/desktop/src/main/main.ts` checks Electron safe storage during bootstrap and throws if the backend is not secure. `SafeStorageSecretProtector` correctly rejects Linux `basic_text`/unknown secure-storage backends.

This matches AppImageHub PR #5987: its offline/sandbox test shows the secure-storage startup error instead of the main window. The same report flags the AppImage as not self-contained, using an old runtime, relying on system C library/libfuse2, and referencing glibc 2.39.

Correct direction: let the desktop boot in a **safe degraded mode** when no secure keyring exists; keep secret-dependent features unavailable. Do not fall back to plaintext.

### 2.2 Fresh installs currently default auto-reconnect ON

Current source has `tunnelAutoReconnect: true` in both the main default settings and renderer default config. Existing docs already describe first-time setup as manual, so the observed Configure/Check → Start problem is a runtime/default-state mismatch, not just documentation.

### 2.3 Dev Mode notice is hard-coded

Guided tunnel setup renders `guidedTunnel.devModeWarning` and existing UI/E2E tests assert it. The user reports ChatGPT Web no longer exposes the old user-facing Dev Mode switch. Remove the stale warning and stale expectations; do not add a replacement text-only test.

### 2.4 Logs overclassify non-success results as errors

`WorkLogEntry.kind` is currently `task | result | error` and `classifyMcpWorkLogKind()` returns `error` for most completed non-success codes. Live logs derive their MCP level from the same kind, while `LogStreamPanel` separately treats every non-`SUCCESS` completion as failed.

IPC already has `LogLevel = info | warn | error`. The cleaner contract is to keep lifecycle/outcome separate from severity and use one shared severity classifier for both pages.

### 2.5 Full IDs are already present in data

Work Log and Live Logs retain full workspace/session IDs; visual layout can ellipsize them. Copy behavior therefore must use the raw canonical ID, never the rendered text.

### 2.6 Recovery backend already supports 3 days

The settings UI currently offers `7, 14, 30, 60, 90, 180, 365`; the backend accepts a broad integer range and already persists/sweeps by `recoveryRetentionDays`. Adding `3` should not require a storage redesign.

### 2.7 External MCP already has session close/disconnect machinery

`packages/extensions/src/mcp-session-manager.ts` owns persistent external MCP sessions and has close/session-replacement logic. `extensions-service.ts` delegates shutdown/disconnect. The fix should find the actual duplicate-spawn seam; it should **not** kill Serena after every tool call because a persistent MCP child is intended.

### 2.8 `exact_sha_ci` / `package` are strict but the receipt bridge is incomplete

`RuntimeEngineeringEvidenceVerifier` resolves an evidence `runId` through status providers, then requires strict canonical proof:

- `exact_sha_ci`: canonical `gh run view ... --json headSha,status,conclusion`, terminal success, exact tracked 40-hex SHA.
- `package`: canonical release-evidence verifier, exact source commit and expected artifact identity/location.

The Watcher symptom is consistent with a truthful durable-shell receipt not being recognized by this provider bridge. Fix the resolver/adapter, not the evidence requirements.

### 2.9 `cross_platform` is a real contract contradiction

The workflow can create a required `cross_platform` gate and the domain marks it as host-observed, but the runtime verifier currently rejects `cross_platform` before checking evidence. A required gate can therefore be generated that the runtime cannot ever prove.

Fix the verifier/evidence contract. Do not bypass it by editing DB state or marking a required proof not-applicable.

### 2.10 Issue #156 has an external trust prerequisite

Issue #156 reports an update installer blocked because the Setup EXE is `NotSigned` and enterprise Code Integrity rejects it. The repo already distinguishes local unsigned development packaging from production Authenticode signing.

A source-code change cannot create a trusted publisher identity. A public Windows release intended to satisfy this case needs a real Authenticode signature from a publisher certificate trusted by the target policy. A local v5.7.3 test installer may remain `NotSigned` when no production signing credential is configured, provided SHA/provenance/release evidence passes and the status is reported truthfully.

### 2.11 Issue #162: Ponytail ULTRA loaded-skill state is intermittently inconsistent

Issue #162 reports `skill_load`/bundled Ponytail activation returning `status=ready`, `ready=true`, followed immediately by `edit_file` or `write_file` rejecting the same workspace/goal as if Ponytail had not been loaded. Rebinding from a sibling worktree to the repo-root workspace does not eliminate the problem, and a small write can succeed before a later write fails.

Correct direction: trace the ToolRegistry loaded-skill activation key/lifetime and mutation-guard lookup. A successful bundled Ponytail load for one workspace/goal must remain authoritative for subsequent guarded mutations in that same scope until the relevant workspace, goal, effective Ponytail policy, or session state genuinely changes. Do not disable or bypass ULTRA enforcement to make writes pass.

## Phase 3 — One severity contract for Work Log + Live Logs

### P3-T1 Separate lifecycle/outcome from severity

Preferred model:

- lifecycle/outcome: task/started vs completed/result;
- severity: `info | warn | error`, reusing existing `LogLevel` where practical.

Conservative mapping:

- **info** — normal starts/successes and normal lifecycle events;
- **warn** — recoverable precondition/validation/probe outcomes that do not indicate an internal runtime failure;
- **error** — actual internal/fatal/dependency/runtime failures, broken invariants, or terminal failures of the requested operation.

Do not globally downgrade every `INVALID_INPUT`, `FILE_NOT_FOUND`, `EXECUTABLE_NOT_FOUND`, or permission failure. Classification may need tool/context-aware rules because a code can be an expected probe in one call and a real failure in another.

- explicit Task/Info/Warning/Error semantics;

- genuine errors remain obvious;
- filters include Warning and Error, not only All vs Error;

## Phase 7 — Engineering Harness gate contract repair

### P7-T1 Trusted durable-shell receipt resolver

Add a first-class resolver/adapter that maps an Engineering `runId` to an **owned terminal** shell/task receipt with bounded structured facts:

- provider/task identity;
- workspace ownership;
- exact executable + argv/command;
- cwd/scope where required;
- terminal state;
- exit code;
- captured stdout needed for structured proof;
- source commit evidence when available.

Reject foreign, stale, non-terminal, mismatched-workspace, mismatched-command, or failed receipts. Caller-supplied `conclusion=success` cannot override a failed receipt. `user_attested` is not a substitute for gates that require host-observed proof.

### P7-T2 Preserve strict `exact_sha_ci`

A receipt can bridge provider status only if it still proves terminal hosted CI success and `headSha` exactly equals the tracked source SHA. Keep `matchesCurrentTrackedSource()` strict.

### P7-T3 Preserve strict `package`

Receipt must still prove canonical release-evidence verification, exact source commit, expected artifact name/platform/arch/location, and real package provenance.

### P7-T4 Make `cross_platform` actually verifiable

Replace the unconditional rejection with an explicit proof model:

1. exact-SHA hosted CI matrix evidence that proves every required target platform/job; or
2. target-host receipt bundle proving each required platform against the same source revision.

If one `EngineeringGateEvidence` record cannot represent this safely, extend the domain schema explicitly (platform observations/receipt refs) rather than hiding JSON in free-form strings.

Rules:

- all required platforms must pass;
- wrong-SHA evidence is stale/rejected;
- one platform never counts for another;
- missing platform stays pending/failed;
- required gate cannot be waived with free-form not-applicable text.

### P7-T5 Restore normal Goal completion

When all required gates have real evidence, `finish_goal(status=completed)` must succeed normally. Reconciliation remains for genuinely abandoned/superseded goals only. No direct DB edits and no fake gate status.

Regression cases:

- valid owned durable receipt accepted;
- foreign/mismatched/non-terminal/wrong-SHA receipt rejected;
- complete cross-platform evidence passes;
- partial platform evidence cannot finish;
- valid gates allow normal completion without reconciliation.

# 6. External dependencies that cannot be faked

- **Windows Authenticode:** a real trusted publisher signing credential must exist for an official signed Windows release. Source code cannot manufacture enterprise trust, and target WDAC policy may additionally need to allow that publisher/root.
- **AppImageHub retest:** the catalog must be able to download the newly published fixed AppImage; a dev push or local Windows installer cannot change the artifact currently tested by PR #5987.
- **Cross-platform proof:** Windows-local execution cannot prove Linux/macOS behavior. Hosted CI or target-host receipts are required.

These dependencies are reasons to keep gates truthful, not reasons to weaken them.
