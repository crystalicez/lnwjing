# lnwjing v5.5.0 — Complete Office Suite Tools + What's New UX Plan

Date: 2026-09-22
Target: lnwjing 5.5.0
Branch when implementation starts: dev
Status: IMPLEMENTATION IN PROGRESS on dev for v5.5.0
Implementation baseline was re-checked before mutation. v5.5.0 now also includes the additive scheduler-resume and MCP connection-transport scope recorded below; those additions must preserve all existing v5.4.x ngrok/OAuth/Secure MCP Tunnel behavior by default.

## Destination

v5.5.0 should turn the existing Office capability into a production-grade Office automation platform that ChatGPT can use directly through lnwjing, while preserving lnwjing permission, Active Project, recovery, audit, capability-readiness, and platform boundaries.

The release has two primary outcomes:

1. Complete, practical Office tooling that can read, create, edit, inspect, validate, convert, compare, and automate supported Microsoft Office / Microsoft 365 workloads with truthful provider capability reporting.
2. A user-facing “What’s New” experience beside the app version that opens a localized release-notes modal for the currently installed version.

“Complete Office tooling” does not mean pretending every platform exposes identical native APIs. It means every advertised action must either work through a verified provider or return an explicit dependency/unsupported result. No feature may silently fall back to UI clicking and report native success.

## Current repository baseline

The existing implementation already provides the foundation and must be evolved rather than bypassed.

Current Office-related surfaces include:

- Generic office capability with excel, word, powerpoint, and outlook apps.
- Generic actions currently include status, read, read_text, sheets, list_folders, list_messages, write, replace, merge, and save_as.

The sidebar also displays the version as static text. v5.5.0 must preserve the current update button behavior and add a separate “?” affordance for release notes rather than overloading the existing version action.

## Product principles

### Truthful capability reporting

Every Office tool must expose provider, readiness, dependency state, supported actions, limitations, and platform. A tool must not claim ready when the installed provider cannot perform the requested action.

### Native structured APIs before desktop UI automation

Preferred order:

1. Native Office object model / local structured provider.
2. Microsoft 365 / Microsoft Graph where the requested workload is actually supported.
3. Open XML / structured file provider where fidelity is sufficient and explicitly reported.
4. LibreOffice UNO where relevant on Linux and where compatibility is validated.
5. Desktop UI automation only as an explicit, separately named fallback when no structured provider exists. It must never masquerade as COM, Graph, or Open XML.

### Backward compatibility

Keep the existing generic office capability operational for existing clients. New high-level tools should route through a shared Office runtime so behavior is not duplicated.

### Bounded model context

Do not return entire large workbooks, documents, mailboxes, decks, notebooks, or sites by default. Every read API must provide paging/ranges/limits and bounded previews.

### Recoverable mutations

File mutations must use the same external-file safety and replacement-backup model already used by docx_merge. A failed operation must not leave a partially replaced source file when an atomic/temp-copy workflow is possible.

### Explicit risk

Reading is not equivalent to sending mail, deleting a meeting, refreshing external data, running VBA, publishing a presentation, or overwriting a document. Mutation and dangerous actions must remain separately classified.

## Target architecture

Create an Office Suite v2 layer rather than adding unrelated one-off tools.

Logical flow:

ChatGPT / MCP client
→ lnwjing tool contracts
→ OfficeSuiteRuntime
→ provider router
→ one verified provider
→ output normalization / bounded result
→ audit + recovery + telemetry

Recommended provider layers:

- Windows Office COM provider: authoritative high-fidelity local provider for installed Microsoft Office apps on Windows.
- macOS Office automation provider: explicit Apple Events / supported native automation only for operations confirmed to work. No fake parity.
- LibreOffice UNO provider: Linux/local document fallback for supported document/spreadsheet/presentation operations.
- Open XML provider: cross-platform structural DOCX/XLSX/PPTX read/write/inspect/compare for operations that can preserve required fidelity.
- Microsoft Graph provider: Microsoft 365 cloud workloads such as Outlook mail/calendar/contacts, OneDrive, SharePoint, OneNote, Teams, and Excel workbook APIs where Graph supports the requested operation.
- UI fallback provider: opt-in only, separately reported, never selected silently.

Provider selection must be deterministic and observable. The result should say which provider handled the request.

## Provider implementation requirements

### Windows Office COM

Windows should be the first full-fidelity target because lnwjing already has a working Windows-native Office capability.

Implementation rules:

- Use isolated owned automation sessions where practical.
- Do not attach to or close a user’s unrelated interactive Office process unless explicitly requested and ownership is proven.
- Release COM references deterministically.
- Prevent orphan WINWORD.EXE / EXCEL.EXE / POWERPNT.EXE / OUTLOOK.EXE processes created by lnwjing.
- Cancellation must stop only lnwjing-owned work.
- Enforce operation timeouts.
- Detect Office not installed / app not installed / file locked / Protected View / modal dialog conditions and return actionable structured errors.
- Never disable Trust Center / Protected View globally.
- File mutations should work on a safe copy and replace only after verification when feasible.
- Preserve original file on failure.

### macOS

The current macOS Office backend is only a dependency boundary. v5.5.0 must implement and test real supported automation before marking actions ready.

Requirements:

- Detect installed Microsoft Office apps.
- Detect Automation permission availability.
- Use supported Apple Events/JXA/native automation paths where reliable.
- Maintain a per-action capability matrix.
- If an action is not supportable with validated fidelity, return unsupported rather than fake success.
- Open XML or Graph may be selected for operations not available through native automation, but the selected provider must be reported.

### Linux

Linux must not pretend that local Microsoft Office COM exists.

Supported strategy:

- LibreOffice UNO for validated local document/spreadsheet/presentation operations.
- Open XML for structural Office file operations.
- Microsoft Graph for Microsoft 365 cloud workloads.
- Per-action capability matrix and truthful limitations.

### Microsoft Graph / Microsoft 365

Add an optional OAuth provider with least-privilege scopes.

Requirements:

- OAuth tokens stored only in secure local storage.
- No access/refresh token in logs, tool outputs, diagnostics, crash reports, or release evidence.
- Scope acquisition should be incremental where possible.
- User can disconnect/revoke local credentials.
- Provider status shows scopes/capabilities without exposing secrets.
- Graph should be used only for workloads actually supported by the Graph API; do not promise full Word/PowerPoint object-model editing merely because the file is stored in OneDrive.
- Cloud file operations must respect Active Project boundaries when downloading/uploading local files.
- Network operations need explicit open-world metadata and audit events.

## Safety, permissions, and recovery

### Permission classes

READ:

- inspect/list/search/read content.
- metadata.
- preview/compare.
- capability/status.

WRITE:

- create/edit/save files.
- create drafts.
- update local/cloud items where reversible.

EXECUTE / elevated side effect:

- print.
- refresh external data.
- long-running exports.
- provider-native calculation/refresh operations that can contact external systems.

DANGEROUS / explicit approval:

- send mail.
- send meeting invites/updates/cancellations.
- delete cloud data or messages.
- permanent delete.
- run VBA/macros.
- overwrite source file without recovery capability.
- change sharing/permissions.
- publish externally.
- any operation that lowers Office security settings — v5.5.0 should normally deny rather than permit this.

### Dry-run

Every mutation-capable Office tool should support dry-run where a meaningful preview can be produced.

Dry-run should return:

- provider that would be used.
- files/items affected.
- operation count.
- destructive/high-risk steps.
- expected output paths.
- required confirmation level.
- dependencies/scopes required.

### File recovery

Reuse or generalize prepareExternalFileMutation.

For existing files:

- create replacement backup before overwrite.
- retain Recovery Trash/checkpoint metadata.
- expose recovery evidence in result.
- verify target exists and is readable after mutation before declaring success.

### Secret handling

Passwords for protected Office files, Graph tokens, mailbox credentials, and tenant secrets must be ephemeral or secure-storage backed. Never echo them into logs or tool results.

## Data and versioning contract for release notes

## Testing strategy

Follow lnwjing’s behavior-focused test rule: create/modify tests only for meaningful functional behavior, contracts, validation, integration, and regression risks. Do not add tests merely for wording, CSS, icon shape, labels, or formatting.

### Unit / contract tests

- schema action validation.
- provider selection.
- capability matrix.
- bounded outputs.
- permission classification.
- dry-run.
- recovery planning.
- secret redaction.
- release-note registry version lookup.
- What’s New modal open/close and locale behavior only where functional behavior is involved.

### Provider tests

Use provider fakes for deterministic CI, but do not treat fakes as proof that native Office works.

Windows real-provider acceptance on an Office-equipped test host should exercise temporary files for Word/Excel/PowerPoint and safe Outlook draft operations.

macOS/Linux acceptance should run only against the real provider being claimed ready.

### Integration tests

- tool registry → Office runtime → provider.
- mutation policy.
- Active Project path enforcement.
- Full Bypass semantics.
- cancellation.
- output recovery.
- Graph OAuth token redaction.
- tool availability/remediation.
- generated tool catalog.

### Desktop functional tests

- version update button still calls update action.
- “?” opens release notes without triggering update.
- modal resolves exact current version.
- locale switch updates modal text.
- keyboard open/close.
- missing release-note entry shows graceful state.

No dedicated test is required merely for the exact tooltip sentence or visual spacing.

Never commit credentials or captured mailbox/document contents as evidence.

## Performance and reliability requirements

- Reuse Office application sessions only when safe; avoid per-cell COM startup.
- Batch range operations instead of one COM round trip per cell.
- Enforce operation-level timeout.
- Support AbortSignal/cancellation where provider can safely stop.
- Long export/refresh tasks expose progress when practical.
- Cache only safe metadata/capabilities, not document content or secrets by default.
- Close/dispose provider resources on success, failure, timeout, app shutdown, and cancellation.
- Telemetry should record tool/provider/action/latency/result code but not document bodies, cell contents, mail bodies, tokens, or sensitive filenames when redaction policy requires masking.

## Security requirements

- Maintain Active Project scoping for local file paths.
- Cloud item IDs are not local-path bypasses.
- Attachments downloaded from Outlook/Teams/SharePoint must pass file-safety boundaries.
- Protected View and Trust Center remain enabled.
- Macros default disabled.
- External data refresh is not automatic.
- Sending/publishing/sharing is explicitly confirmed.
- Provider errors must not dump COM objects, OAuth tokens, HTTP authorization headers, or raw sensitive payloads.
- Office-generated temporary files use owned temp locations and are cleaned safely.
- Do not invoke shell scripts for text/document mutation when native/structured provider actions exist.

## Backward compatibility and migration

- Existing office primitive remains callable.
- Existing inspect_workbook/render_excel_preview/compare_workbook_layout remain valid; they can delegate internally to OfficeSuiteRuntime.
- office_ppt and office_outlook remain valid aliases or compatibility tools until a documented deprecation cycle.
- docx_merge remains compatible and should route through office_word merge logic after parity is proven.
- Tool result shapes should preserve existing fields where clients may rely on them, while adding provider/readiness metadata additively.
- No saved user setting should be deleted as part of the Office migration.

## v5.5.0 acceptance criteria

The release is complete only when all of the following are true:

1. Existing Office tools remain backward-compatible or have explicit compatibility aliases.
2. office_status truthfully reports app/provider/action readiness.
3. Word can create, read, materially edit, save, export, inspect, and recover a DOCX through at least one verified provider.
4. Excel can create, read/write formulas and formatting, perform table/chart operations, save/export, inspect, and verify affected ranges.
5. PowerPoint can create/edit real slides with text/media/table/chart operations and export/inspect the deck.
6. Outlook can read/search messages and create/edit drafts; send/delete remain confirmation-gated.
7. Calendar/contact/task capabilities are exposed only where the provider actually supports them.
8. Microsoft 365 OAuth is secure and tokens never appear in model-visible output/logs if Graph support ships in v5.5.0.
9. OneDrive/SharePoint/OneNote/Teams actions advertised as ready have real-provider evidence.
10. Access/Visio/Project/Publisher are dependency-gated optional tools and never falsely report ready.
11. Every Office mutation has a correct permission classification and recoverable-file strategy where applicable.
12. Macro execution is disabled by default and cannot be enabled silently.
13. Large Office reads are bounded/paged.
14. Real-provider acceptance has been run for every provider/app advertised as production-ready.
15. The title-bar version retains its existing update/check/install behavior.
16. A separate “?” button is visible beside the title-bar version.
17. Hover/focus on “?” shows localized “ดูกันว่ามีอะไรอัพเดตใหม่” / “See what’s new”.
18. Clicking “?” opens an accessible modal for the exact installed version.
19. Release-note modal supports Thai and English through the shared i18n system with no local isTh/locale branching.
20. Release notes are grouped into clean categories and empty categories are hidden.
21. Missing release-note data fails gracefully without showing the wrong version.
22. v5.5.0 ships with a finalized local release-note entry.
23. Tool catalog/docs/version contracts are regenerated and release checks pass.
24. No unrelated v5.4.x working-tree work is overwritten during implementation.
25. `search_text` treats query text as literal/fixed-string by default; characters such as `(){}?+*` do not become regex unless `regex: true` is explicit.
26. Valid explicit regex remains supported, while malformed regex/glob input returns a readable structured recoverable error with a retry suggestion.
27. `edit_file` remains exact-match only and never chooses a fuzzy candidate automatically.
28. Exact-edit conflicts are recoverable and distinguish multiple-match, stale-content, and text-not-found cases through structured conflict metadata.
29. Exact-edit mismatch responses detect and report CRLF/LF or whitespace-only drift when present.
30. A zero-match exact edit returns bounded nearby candidate context when available plus a re-read/retry suggestion, without mutating the file.
31. Regression coverage proves literal `failureLegacyBotName()` search, explicit regex behavior, malformed-regex recovery, stale exact-edit safety, line-ending/whitespace diagnostics, and recoverable conflict responses.

## Implementation guardrails for the future coding session

Before editing important Office logic:

- Activate the exact workspace in Serena and confirm Active Project.
- Inspect references/implementations for existing office, document runtime, capability provider, tool registry, mutation policy, AppShell, update action, and i18n symbols.
- Re-check this plan against the then-current dev HEAD.
- Keep existing safety/recovery abstractions instead of building parallel ones.
- Prefer shared provider/runtime components over app-specific duplicated plumbing.
- After logic changes, run targeted diagnostics and the smallest relevant functional/integration tests.
- Do not create tests for copy/CSS-only changes.
- Before release, run real-provider acceptance in addition to mocks/unit tests.

## Explicit non-goals

- Do not claim 100% feature parity across Windows, macOS, Linux, COM, Graph, UNO, and Open XML when the underlying APIs differ.
- Do not disable Office security mechanisms to make automation easier.
- Do not make computer_use the default implementation for Office document editing.
- Do not expose OAuth tokens or document/mail contents through telemetry.
- Do not auto-send mail, invites, Teams messages, or sharing links.
- Do not auto-run macros.
- Do not couple opening the What’s New modal to a network request.
- Do not replace the existing version update button with the release-notes button.
- Do not make `edit_file` silently fuzzy-match or auto-select among multiple candidate edit locations.
- Do not interpret `search_text` query strings as regex unless the caller explicitly requests regex mode.

## Definition of done

v5.5.0 is done when ChatGPT can use lnwjing as a truthful, permission-aware, recoverable Office automation layer for the Office/Microsoft 365 workloads that the installed providers actually support; the major Word/Excel/PowerPoint/Outlook workflows are verified against real providers; optional apps/cloud workloads expose exact readiness rather than fake parity; search/edit primitives recover safely from regex and stale-context errors without unsafe fuzzy edits; and end users can click the “?” beside the current version to read a clean Thai/English categorized summary of what changed in that installed release.
