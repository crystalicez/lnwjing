## Contract decisions

1. Engineering Harness is opt-in and defaults Off. Invalid/future persisted settings resolve Off with a visible diagnostic.
2. The feature is a policy/workflow projection over existing settings, project profile, ToolRegistry, and durable goals. Do not introduce a second task database.
3. Lightweight low-risk edits remain lightweight; no speculative tests, durable goal, or schedule solely because Harness is enabled.
4. Substantive Engineering Harness tasks use the existing durable goal authority and existing intent revision/checkpoint/acceptance APIs.
5. Engineering Harness itself never authorizes a Native ChatGPT Scheduled Task. `engineering_start_task` must request `scheduledContinuation=off` unless the task has separate explicit scheduling authority.
6. A central Engineering preflight guard is added only after existing workspace/security/mutation routing. It never grants permission or bypasses Active Project, recovery, destructive policy, or goal-lease fences.
7. Project files may refine or disable Engineering Harness but cannot enable it against user opt-out. Global/workspace user settings remain the activation authority.
8. Code-intelligence routing is capability-based: repository CodeGraph-first instruction when applicable, then callable semantic/LSP tools, then ordinary search. Missing optional tools are reported truthfully.
9. Evidence is host-observed when possible and tied to workspace/source identity. Pending, unknown, running, failed, blocked, or stale evidence cannot be represented as passed.
10. Version/release work begins only after functional behavior and deterministic regressions are complete; canonical version tooling and repository release rules remain authoritative.

## First-party mutation surface for Phase 6 inventory

Mechanically classifiable routes already pass through `ToolRegistry` mutation policy, including structured file writes/replacements/deletes, Git mutations, shell/WSL/process execution, durable automation mutation, external MCP calls, native UI/input mutations, web writes, scheduler mutation, Office mutation, plugin/hook/config persistence, worktree mutation, and other unclassified WRITE/DANGEROUS tools that currently fail closed as opaque mutation.

Engineering preflight must exempt read-only discovery, settings recovery, Engineering prepare/status reads, and goal acquisition. Batch dispatch remains guarded per child call. Unknown mutation routes in strict Engineering contexts must remain conservative rather than being described as universally enforced.

## Validation ladder

Use the smallest level that can prove the changed behavior, escalating by risk and delivery scope:

1. diff/static check;
2. affected existing/focused tests;
3. package tests plus typecheck/lint where applicable;
4. integration/acceptance;
5. cross-platform/full gate;
6. build/package;
7. installed or production-like runtime.

The repository's existing test guidance remains authoritative: behavior-oriented regressions, target-host evidence for platform claims, fail-closed security tests, and no timeout inflation as a substitute for a root-cause fix.

## Phase 0 exit condition

Phase 0 is complete when this contract remains consistent with the implementation checkout, the settings/goal/mutation seams above are confirmed, and the Phase 1 implementation starts without introducing duplicate state or weakening repository safety contracts.
