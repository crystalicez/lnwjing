# lnwjing v5.7.0 — Engineering Harness Implementation Plan

Date: 2026-09-28
Target: 5.7.0
Status: plan only; no implementation or version change in this document
Implementation branch: `dev` under the repository's normal workflow

**Goal:** A user who explicitly enables Engineering Harness can describe a software task in natural language and receive a proportionate, evidence-backed workflow across coding projects: discover → analyze → plan → implement → validate and repair → review → deliver within the requested scope. Existing users keep their current behavior.

**Architecture:** Extend the current settings, project detection, skill catalog, MCP server, `ToolRegistry`, and durable goal/checkpoint services. Keep one authoritative durable goal for substantial work; Engineering Harness adds a policy and workflow projection over it, not another independent task database. Lightweight tasks use a short-lived context and do not create a durable goal or schedule merely because the setting is on.

**Stack:** TypeScript 6, Node 24, pnpm 10.15.0, Electron/React, MCP, SQLite, Vitest, existing Windows/macOS/Linux CI and packaging gates.

## 1. Product decision and release boundary

- Default is **Off**. Enabling is an explicit user action in Settings. Recommended first-use preset is **Senior**; Standard, Strict, and Custom are available.
- Apply automatically to software-engineering requests in coding workspaces. An advanced “all workspaces” option changes where detection runs, but a spreadsheet, writing, or ordinary file request still follows its own appropriate workflow.
- The user may disable Harness for a workspace in lnwjing's own settings. A repository file cannot silently turn it on when the user has opted out.
- Start from the task's actual scope. “Fix locally” does not imply commit, push, PR, merge, tag, release, deployment, or scheduled continuation. Each later boundary needs an instruction that covers it.
- Provide a light path for copy, CSS, icons, docs, and tiny mechanical edits. High-risk auth, persistence, permissions, concurrency, data migration, security, and release work receives stronger analysis and validation.
- Reuse existing `AGENTS.md` and `.lnwjing/project-profile.json`. Do not create a competing `.ai/` hierarchy or a second `.lnwjing/engineering.yaml` in 5.7.0. Automatic bootstrap means a cached/app-managed project assessment; writing repository files is a separate explicit action with a diff preview.
- No hard dependency on Serena, Wayfinder, CodeGraph, or a particular external skill. When `.codegraph/` exists, follow that repository's instruction to use it first. Otherwise use available symbol/LSP tools or ordinary search, and report the method actually used.
- This feature governs work performed through lnwjing's MCP/runtime surfaces. A host that bypasses lnwjing tools cannot be truthfully described as mechanically governed by this Harness.
- This plan does not authorize implementation, Git upload, version bump, deployment, or a scheduled task now. The final release phase below is future work only.

## 3. User journeys and observable acceptance

1. **Normal user:** install or upgrade and never enable Harness. Settings default Off; general tools, permission profiles, MCP behavior, and non-coding tasks remain as before. No new repository file, background goal, or recurring schedule appears.
2. **First enable:** turn on Engineering Harness in Settings, accept Senior, open a coding workspace, and give a natural-language request. The client receives effective policy, task kind, risk, required steps, selected tools, and the reason for each required gate without a long setup wizard.
3. **Small edit:** “fix About page typo” yields inspect → edit → diff check. It creates no speculative test and does not demand architecture review or package builds.
4. **Behavioral bug:** “first Start click fails” yields reproduction/trace, root cause, affected references, a focused regression only if existing coverage does not protect the failure, diagnostics, and review appropriate to risk.
5. **High-risk change:** “change token persistence” identifies auth/persistence risk, tests restart and failure behavior, checks security and cross-platform impact, and does not mark done while required evidence is missing.
6. **New requirement mid-task:** “also remember web sessions for 60 days” increments intent revision, updates acceptance/validation and affected plan steps in the *same* durable goal, and preserves proven earlier work.
7. **Reconnect or new worker:** resume from authoritative goal, checkpoint `resumeContext`, current policy, tracked task status, and exact next action. No duplicate build/watch task is launched on guesswork.
8. **User chooses no schedule:** Harness still works and can use a durable goal with `scheduledContinuation=off`; enabling Harness by itself never authorizes an hourly task.
9. **Workspace override:** a user-managed workspace Off switch wins over global On. Repository project metadata can refine commands/profile but cannot silently re-enable the feature.
10. **Limited host capability:** missing CodeGraph/Serena/Wayfinder/CI is shown as unavailable or not applicable. The result never claims a tool, suite, installed runtime, or remote check ran when it did not.

## 4. Chosen approach and alternatives considered

| Approach | Benefit | Limitation | Decision |
| --- | --- | --- | --- |
| One global Skill or prompt | Easy to ship | Cannot persist task state, validate evidence, or guard tool mutation | Use only as concise guidance |
| Separate workflow database plus many `engineering_*` tools | Full bespoke model | Duplicates durable-goal state, lease, checkpoints, migrations, and UI semantics | Reject for 5.7.0 |
| Opt-in policy service over current goal and registry | Uses existing safety and persistence seams; measurable rollout | Requires careful Desktop/STDIO parity and host cooperation | **Choose** |

The initial 5.7.0 product is a reliable local/MCP engineering workflow. Organization policy distribution, arbitrary language dependency-graph analysis, remote-agent control outside lnwjing, and automated deployment are extension points rather than unverified release claims.

## 5. Effective policy contract

### 5.1 Source and precedence

1. Host security, permission, Active Project, recovery, durable-goal lease, and release protections remain authoritative. Full Bypass keeps its existing approval/scope semantics but does not bypass an active rolling goal's `goalLease` fence.
2. Explicit current user instruction defines requested outcome and delivery scope. A task request may narrow checks where there is no hard host requirement; it cannot convert a skipped/failed check into a pass.
3. User-controlled global and workspace Harness settings determine whether the feature runs and which preset applies. A workspace Off override wins over global On; an explicit workspace On override is a user opt-in even if global Off.
4. Project `AGENTS.md` and `.lnwjing/project-profile.json` provide architecture, commands, platform facts, and project checks. A repository `engineering.mode: off` is an explicit project override and must be shown in status; a profile value may strengthen but never lower the user's selected Standard/Senior/Strict level. Treat content as workspace data/instructions at its existing trust level; never let it grant permissions, force publication, reveal secrets, or enable Harness against an explicit user opt-out. A mid-task repository change to `off` does not silently release an active goal or its gates.
5. A future organization layer, if added, may only strengthen a host-enforced floor. 5.7.0 has no pretend organization-policy support.

At task start, resolve and return `enabled`, `source`, `profile`, `workspaceId`, `taskKind`, `risk`, `workflow`, `requiredGates`, `selectedCodeIntelligence`, `deliveryScope`, `policyDigest`, and a concise list of reasons. Re-resolve at task start/resume and when Settings, `AGENTS.md`, or the project profile changes. A changed digest invalidates dependent planned gates and requires a checkpoint/replan before further code mutation.

### 5.2 Global settings and presets

Persist one bounded, schema-versioned setting (`engineering_harness_settings_v1`) with a safe parser. Shape for implementation:

```ts
type EngineeringProfile = 'standard' | 'senior' | 'strict' | 'custom';
type EngineeringApplyTo = 'coding_projects' | 'all_workspaces';
interface EngineeringHarnessSettings {
  readonly schemaVersion: 1;
  readonly enabled: boolean;                 // default false
  readonly profile: EngineeringProfile;       // default senior when enabled
  readonly applyTo: EngineeringApplyTo;       // default coding_projects
  readonly autoProjectAssessment: boolean;    // app metadata only; default true
  readonly custom?: {
    readonly analysis: 'focused' | 'cross_file';
    readonly review: 'risk_based' | 'always';
    readonly validation: 'risk_based' | 'strict';
    readonly docsImpactCheck: boolean;
  };
}
```

`Standard`: short analysis, affected validation, review only when risk requires it. `Senior`: inspect architecture/references for important logic, meaningful regression tests, proportionate review and documentation check. `Strict`: every applicable hard gate is evidenced before completion, including independent review for high-risk code. `Custom`: only the listed workflow intensities vary; it cannot switch off security, permissions, goal leases, or explicit project release gates. Store this separately from permission-profile settings; “Strict” is an engineering preset, not a permission profile.

### 5.3 Project assessment and project profile

- Reuse `ProjectService` and extend detection beyond `package.json` to bounded, read-only recognition of `pyproject.toml`, `Cargo.toml`, `go.mod`, `composer.json`, Maven/Gradle, and `.sln`/`.csproj`; use manifest signals rather than `.git` alone to distinguish software work from general folders.
- Record confidence and why a project was classified. Unknown or ambiguous workspace stays normal or asks for an explicit user choice; it is never silently treated as a software project on a weak signal.
- Discover candidate build/test/lint commands from manifests and existing project docs. Mark them `suggested` until confirmed; discovery must not execute scripts or write files. A command copied from repository content still goes through normal shell/process approval and scope checks.
- Cache the read-only assessment in app-managed workspace metadata keyed by workspace ID and manifest/instruction fingerprints, with bounded invalidation; do not store a generated copy of project rules in the repository.
- Read the existing root `AGENTS.md` afresh when starting/resuming a substantive task. Read a nested `AGENTS.md` only for files within its directory scope. Preserve the established instructions hierarchy; cap bytes and expose truncation as a warning, never silently treat truncated text as complete.
- Extend existing `.lnwjing/project-profile.json` with an optional `engineering` object. Example:

```json
{
  "ponytail": { "mode": "lite" },
  "engineering": {
    "mode": "inherit",
    "profile": "strict",
    "commands": { "test": "corepack pnpm@10.15.0 test" },
    "architecture": { "checkCommand": "corepack pnpm@10.15.0 lint" },
    "requiredPlatforms": ["win32", "darwin", "linux"]
  }
}
```

`engineering.mode` accepts `inherit` or `off` from the repository; only lnwjing's user-controlled Settings may explicitly turn a workspace On. Validate sizes, keys, known enums, path containment, and secret-bearing fields through the existing project-profile normalization path. Preserve unrelated keys and the user's formatting as far as practical. No automatic write to the repo on detection; an optional “Save project profile” action previews the exact diff and uses existing mutation/recovery policy.

Architecture checks are project-specific. The Harness inspects dependency impact, records the relevant existing project command (for example lint or an architecture check), and runs it through ordinary execution permissions when applicable. For JavaScript/TypeScript projects, 5.7.0 may add a small explicit forbidden-import rule only if it has a clear package boundary and deterministic parser/test; it must not infer a universal clean-architecture rule from folder names. For other languages, use a declared project check or report that no machine-checkable architecture rule is configured. Human review still covers boundaries that the configured check cannot observe.

## 6. Task workflow and data contract

### 6.1 Task classification and routing

Supported task kinds: `feature`, `bugfix`, `refactor`, `review`, `incident`, `release`, `maintenance`, `docs`, `unknown`. A task may carry multiple labels (for example `bugfix` + `security`), but one primary kind chooses the base workflow. Classification uses the user request and verified workspace facts, never a filename keyword alone. When confidence is low, choose the smallest safe discovery step and expose uncertainty; the user can correct the classification in the current task.

| Primary kind | Required sequence before implementation | After implementation |
| --- | --- | --- |
| Feature | requirement and affected contracts → current architecture → impact/risk → plan | focused validation → integration when applicable → review/docs |
| Bugfix | reproduce or state why unavailable → trace → root cause → references → fix plan | regression evidence for the actual failure → diagnostics/review |
| Refactor | current behavior/invariants → callers → migration/backward compatibility plan | existing behavior tests → architecture/dependency check → review |
| Review | exact diff/base and scope → inspect affected paths | findings with source evidence; no mutation unless requested |
| Incident | observed failure and timeline → containment/scope → root cause | verified recovery and follow-up evidence |
| Release | exact source SHA and authorized delivery boundary → existing release process | exact-run CI/artifact/signature/provenance evidence |
| Docs/low-risk maintenance | inspect target and nearby conventions | diff/format/link check only where relevant |

Bound the loop: failed validation means inspect the exact failure, diagnose, fix, and rerun the relevant gate; do not merely raise timeouts or rerun blindly. Stop with a truthful `blocked`/`failed` result if a required host, credential, platform, external service, or user decision is unavailable. “Continue until passes” is not permission to fabricate evidence, weaken a gate, or loop indefinitely.

### 6.2 Risk rubric and test rule

Risk is a reasoned tier, not a test-count target. Record triggers and allow escalation when discovery changes the assessment.

| Tier | Example trigger | Minimum planning/validation |
| --- | --- | --- |
| Low | copy, docs, CSS-only, icon, harmless rename | target/diff check; no new test unless visible behavior truly changes |
| Medium | local behavior or public UI workflow | inspect existing tests; focused behavior test if an uncovered regression exists; typecheck/lint for affected code |
| High | API contract, data persistence, auth, permissions, cross-process lifecycle, concurrency, cross-platform native path | affected references; deterministic regression or integration proof; relevant full gates; independent review |
| Critical | destructive/data migration, credential boundary, release or production deployment | failure/rollback path, recovery/provenance and exact environment evidence; release-specific gates and explicit delivery authority |

Before adding a test: identify the observable behavior and failure mode; inspect existing coverage; choose the lowest layer that can actually fail for that regression; add one focused test only when coverage is missing. Do not create tests for coverage percentage, labels, copy, CSS spacing, icons, comments, formatting, or private implementation details by default. A bug that cannot be reproduced locally still needs a documented failure hypothesis and suitable contract/integration evidence or a truthful blocker.

Verification ladder: (1) diff/static checks, (2) affected existing/focused tests, (3) package tests and typecheck/lint, (4) integration/acceptance, (5) cross-platform/full gate, (6) build/package, (7) installed or production-like runtime. Select the highest necessary level from risk and delivery scope. Do not claim a lower level proves a higher level; platform simulation is not native-host evidence.

### 6.3 Durable state, task evolution, and scheduling

- Trivial tasks may return an ephemeral `EngineeringTaskContext` without a goal. Any multi-step task that needs checkpoint/resume, long-running validation, or guarded mutation uses existing `run_goal`/goal service with an engineering namespace. Do not persist a second `EngineeringRun` aggregate.
- Namespaced metadata should contain only data absent from the goal today: `schemaVersion`, `primaryTaskKind`, `riskTier`, `policyDigest`, `deliveryScope`, and gate definitions. Existing goal `objective`, `plan`, `acceptanceCriteria`, `userIntentRevision`, `currentPhase`, `evidence`, `trackedTasks`, `resumeContext`, and lease remain authoritative.
- Start by binding goal/workspace/client session. Use the existing lease/revision compare-and-swap for every checkpoint and engineering metadata change. A reconnecting worker must reacquire ownership via the existing rules. Never infer ownership from MCP session identity alone.
- A mid-task user correction calls the existing intent revision path, updates affected plan and acceptance criteria, marks invalidated gates stale, checkpoints changed files/decisions/failed attempts/pending validation/exact next action, and keeps settled unrelated steps.
- Harness opt-in does **not** opt the user into Native ChatGPT Scheduled Tasks. For Harness-created manual goals pass `scheduledContinuation=off`; keep existing scheduled-continuation behavior for tasks that separately authorize it. If a rolling goal is active, every mutation still carries current `goalLease`; do not create a new scheduler or bypass lease protection.
- Long-running CI/process work uses goal-relative `trackedTasks`, distinguishes `blocking_job` from `supporting_service`, and records exact task/run IDs. The existing authoritative CI watcher policy applies to any required GitHub Actions run.
- No goal is marked complete until required acceptance criteria and engineering gates are terminal. A `skipped` or `not_applicable` gate must include the reason; `not_run`, `unknown`, and `running` never count as `passed`.

### 6.4 Tool and host contract

Expose a small first-party surface instead of the ten speculative tools in the early conversation:

1. `engineering_prepare_task` (read-only): given `workspaceId` and user objective, return project assessment, effective policy, task kind/risk, workflow, gate plan, selected code-intelligence adapter, and digest. No repository write, process launch, goal, or schedule.
2. `engineering_start_task` (state mutation): for a substantive task, create/resume the existing goal with `scheduledContinuation=off` unless the request carries separate, verified scheduling authorization; return goal ID, lease/proof, plan projection, and next action. Reuse the existing `run_goal` service path rather than duplicating lease logic.
3. `engineering_get_status` (read-only): return effective policy source, goal phase/acceptance/gates, observed evidence, blockers, stale gates, and delivery boundary. UI and MCP use the same projection.

Use existing `revise_goal_intent`, `update_goal_plan`, `update_goal_acceptance`, `checkpoint_goal`, `get_goal`, and `finish_goal` for state changes. Put the Engineering DoD check inside the goal-completion path for goals bearing engineering metadata, so a client cannot evade it by calling `finish_goal` directly. A lightweight task has no durable completion claim beyond the final response and observed local checks.

Server instructions advertise the feature only when user settings make it active and should ask clients to prepare before coding mutation. They are guidance, not proof of enforcement. Live settings changes must update the client-visible policy/status without requiring a silent stale prompt; document any reconnect needed for a server-instruction refresh.

## 7. Quality, security, and delivery rules

### 7.1 Evidence and Definition of Done

Each gate records `id`, `applicability`, `status` (`pending`, `running`, `passed`, `failed`, `blocked`, `not_applicable`, `stale`), reason, observed source, timestamp, workspace/commit identity, command or workflow run ID when applicable, exit/conclusion, and a bounded artifact/log pointer. Separate host-observed evidence from model narrative and user-reported evidence. Sanitize secrets and avoid storing raw large logs in goal rows. When code or policy changes, gate evidence tied to an earlier diff/HEAD becomes stale unless a gate's scope demonstrably remains unaffected.

Completion requires: requirements satisfied; root cause addressed for a bug; applicable tests/gates passed; no unresolved blocking review finding; docs checked/updated when behavior changed; requested delivery scope reached; no blockers or live blocking jobs; scheduled cleanup terminal if scheduled continuation was used. The status must distinguish `ready locally`, `PR checks pending`, `released`, and `blocked`; no single green badge obscures the boundary.

Review is a separate phase after implementation. Self-review covers diff, compatibility, side effects, and missing tests. Independent review is required by risk/profile when an authorized reviewer/tool is available. Findings must be verified against current source; rejected false positives are recorded with reasons. A review tool unavailable on the host is a visible gate disposition, never a fake completed review.

Documentation gate asks whether README/README_TH, API/configuration, architecture, troubleshooting, migration, release notes, or user-facing help changed. “No docs needed” records a reason; it does not trigger a placeholder document.

### 7.2 Registry guard and escape boundaries

- Add one central engineering-preflight admission hook in `ToolRegistry` after workspace routing and existing security/mutation checks, using the same mutation classification already available there. Guard only first-party tool-mediated software-project mutations while Harness is effective; avoid blocking read-only discovery, `engineering_prepare_task`, goal acquisition, or settings recovery (no deadlock).
- Associate a prepared task with workspace, client/session, policy digest and goal revision; ambiguous concurrent tasks must supply an explicit engineering task/goal identity. On missing/stale preflight, return a clear `engineering_preflight_required`/`engineering_policy_changed` recovery response, not a generic permission denial.
- Keep existing permission approval, destructive-file safety, Active Project, Full Bypass semantics, and rolling-goal lease checks. Engineering state never grants permission and cannot be used as an approval token.
- Opaque shell commands, external MCP tools, native provider calls, and direct host file access may escape fine-grained code classification. For 5.7.0, name the guarded first-party routes, treat unknown mutation routes conservatively when strict mode is active, and report unsupported enforcement instead of claiming universal coverage. Regression-test route classification, bypass attempts, and multi-workspace isolation.
- Repository files and skill text must be treated as lower-trust input for host actions. Bound content, reject path traversal/symlink escapes through existing path guards, and never auto-run detected scripts or auto-load untrusted external skills. Do not persist secrets in policy snapshots, checkpoints, UI status, or audit.

### 7.3 Settings and workspace UX

Add a distinct **Engineering Harness** Settings section with Thai/English labels: Off switch, preset selector, “coding projects only” default, advanced all-workspace scope, simple explanation of automatic assessment, workspace override, and a read-only effective-policy preview. Show a small workspace status with current workflow/risk/phase, required checks and their evidence state. Explain why Harness is inactive (Off, non-code task, ambiguous project, disabled workspace, missing capability) without alarming general users. Custom options expose only documented choices and the UI never labels a pending check green.

Avoid ten default-on checkboxes and a generated `AGENTS.md` at first enable. Offer a separate “Save project profile” action only after previewing the file and confirming the existing mutation path. Maintain keyboard access, focus, screen-reader labels, narrow-window behavior, and both supported locales.

## 8. Implementation phases

Each phase ends in a reviewable, independently testable deliverable. Exact line ranges and names must be rechecked against the implementation checkout. Run focused tests while building, then expand only for affected risk and the final release gate.

## 9. Test matrix and review gates

| Seam | Test that matters | Avoid |
| --- | --- | --- |
| Settings/IPC | old DB defaults Off; malformed setting rejected; Desktop/STDIO agree | snapshots of every label |
| Project detection | manifests, weak signal, unreadable/truncated instructions, no write | one test per filename with identical behavior |
| Policy | user opt-out, project restriction, task scope, policy digest refresh | tests that only restate an enum |
| Workflow | typo vs auth persistence vs bug vs review-only yields different gates | tests coupled to private classifier token weights |
| Goal/task evolution | same goal and intent revision; stale gate invalidation; lease conflict | fake success via mocked counters only |
| Evidence/DoD | failed/pending/stale cannot finish; observed exact result can finish | model narrative as proof |
| Registry safety | guarded first-party mutation, Full Bypass lease, multi-workspace and STDIO | broad rewrite of unrelated tool authorization |
| UI | effective status, pending vs passed, accessible toggle and save/error | pixel-specific tests for harmless spacing |
| CI/release | exact SHA/run/artifact and target-platform evidence | “latest branch run” or local pass as hosted proof |

Reviewer questions at each phase: Is the behavior real and observable? Is a new test protecting a plausible regression? Did policy or state duplicate an existing authority? Can old users and old goals still work? Are unavailable capabilities represented honestly? Is the proposed delivery action inside the user's scope?

## 10. Migration, rollout, and failure handling

- Database/settings migration is additive. On 5.6.x upgrade, missing Harness setting resolves Off. Existing goals lacking engineering metadata retain their current completion rules. No background migration writes project files.
- A malformed app setting fails closed to Off and shows an actionable diagnostic. A malformed project profile does not erase unrelated settings; it blocks only that profile's engineering override and explains why.
- Toggle Off during an active engineering goal stops new Harness enrollment for future work but does not silently mark the active goal done, cancel its process, drop a rolling lease, erase evidence, or bypass its completion gates. The UI offers resume/finish/cancel through existing goal semantics. A mid-task project-profile Off change follows the same rule. Explicit user scheduling disable stops only scheduling.
- A missing optional code-intelligence or review provider triggers a recorded fallback/disposition. A missing *required* platform or integration environment leaves a blocker, not a fabricated pass.
- Any first-party route discovered to bypass the registry guard is either brought into the covered route set before release or documented as unsupported with a targeted regression test; do not ship a universal-enforcement claim.
- Feature can be disabled in Settings without data loss. Keep goal records/checkpoints for audit/recovery under existing retention behavior; do not invent a new data store to clean up.

## 11. Definition of done for the 5.7.0 feature

The release candidate is ready only when all of the following are true:

- [ ] Default-off upgrade and ordinary non-developer workflows are unchanged by verified tests and smoke checks.
- [ ] Natural-language feature, bugfix, refactor/review, low-risk edit, and high-risk persistence journeys produce proportionate and explainable plans.
- [ ] Global/workspace/project policy precedence is deterministic, bounded, and visible; repository content cannot enable the feature against user opt-out.
- [ ] Substantive work reuses durable goals with correct lease/revision and requirement evolution; simple work avoids unnecessary durable ceremony.
- [ ] Required validation/review/docs/CI evidence is observed and stale-aware; direct `finish_goal` cannot bypass Engineering DoD.
- [ ] First-party mutation guard, permission/scope/recovery, Full Bypass, and rolling `goalLease` interactions have meaningful regression coverage.
- [ ] Settings and status work in Thai/English, Desktop and STDIO behavior agree, and unsupported external-host enforcement is stated plainly.
- [ ] Focused and final applicable checks pass on the exact source being delivered, with target-host proof for platform claims.
- [ ] Version is changed by the canonical script only after functionality is complete, and the separate release process is followed only to the boundary the user has authorized.

## 12. Deliberate non-goals for 5.7.0

- Installing or requiring Serena, CodeGraph, Wayfinder, or third-party review tools on every user machine.
- Controlling direct shell/editor/agent actions that do not pass through lnwjing; the status must say when a host is outside the guarded surface.
- Automatically modifying every project's `AGENTS.md`, creating a new policy tree, or executing detected project commands at discovery time.
- Treating all code edits as requiring a new test, full suite, independent review, package, CI, or release.
- Automatic push, PR, merge, tag, release, deployment, or scheduled continuation from the Harness toggle.
- Organization policy distribution, generalized cross-language architecture dependency graph enforcement, and a second EngineeringRun persistence engine.
