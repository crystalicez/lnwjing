# v5.7.0 Scheduled Continuation: ใช้รอบทำงานให้คุ้ม Implementation Plan

> **For agentic workers:** ใช้ `executing-plans` ทำทีละงานหลังผู้ใช้อนุญาตให้ลงมือเท่านั้น ห้ามส่งงานไปให้ subagent โดยไม่ได้รับคำสั่ง และต้องใช้ `lnwjing-scheduled-continuation` เมื่อทดสอบงานที่ผู้ใช้อนุญาตให้ตั้งเวลา

**สถานะ:** ลงมือทำตามแผนบน `dev` แล้วใน v5.7.0 ตามคำสั่งผู้ใช้ ณ 2026-09-28; ไม่ได้เปลี่ยน cadence/สร้าง Scheduled Task เพิ่ม และขอบเขตส่งมอบรอบนี้คือ commit + push `dev` เท่านั้น (ไม่ merge/tag/release). Host stop reason ของรอบสั้นเดิมยังไม่มีหลักฐานจากโฮสต์ที่ชี้สาเหตุได้แน่ชัด จึงไม่อ้างว่า repo สามารถรับประกัน runtime 30+ นาทีได้.

**เป้าหมาย:** เมื่อ watchdog รายชั่วโมงรับงานที่ยังทำต่อได้ ให้ทำงานที่มีประโยชน์ต่อในเทิร์นเดียวให้นานเท่าที่โฮสต์และเครื่องมืออนุญาต โดยไม่หยุดหลัง milestone/ข้อความอัปเดต; ถ้าโฮสต์บังคับจบ ให้คงสถานะและรับช่วงอย่างปลอดภัย ไม่อ้างว่าจะรันเกินข้อจำกัดที่ยังไม่ทราบ

**สถาปัตยกรรม:** Native ChatGPT Scheduled Task เดิมเป็นผู้ปลุกหนึ่งงานรายชั่วโมง; Durable Goal, lease และ checkpoint ใน lnwjing เป็นผู้ถือสถานะงาน. แก้ตรงสัญญาการทำงานของ worker และ prompt ของ watchdog ก่อน; ใช้หลักฐานจากโฮสต์แยก voluntary yield, tool/connector error, งานที่ยังรันอยู่ และ host cutoff. ไม่เพิ่ม scheduler อีกตัว

**เทคโนโลยี:** TypeScript, Vitest, MCP plugin, SQLite Durable Goal, Native ChatGPT Scheduled Tasks, PowerShell/Windows release gate

## งานวิจัย OpenAI ณ 2026-09-28

1. [Scheduled tasks](https://learn.chatgpt.com/docs/automations) ระบุว่างานในแชตเดิมกลับมาพร้อม context, ใช้ skill/plugin/connected tools ได้ และเลือก minute-based interval สำหรับ follow-up loop ได้; คู่มือแนะนำให้ทดสอบ prompt แบบ manual ก่อนและตรวจ run แรก ๆ. เอกสารนี้ **ไม่ได้ประกาศ** ระยะทำงานสูงสุดต่อ scheduled run หรือวิธีเพิ่มเป็น 30+ นาที
2. [Long-running work](https://learn.chatgpt.com/docs/long-running-work) แนะนำ outcome/constraints/definition of done และ Goal mode ใน desktop, CLI, IDE; สำหรับ hosted web ให้ใช้ ChatGPT Work. เป็นแนวทางจัดงานยาว ไม่ใช่สวิตช์เพิ่ม runtime ของ Native Scheduled Task
3. [MCP configuration](https://learn.chatgpt.com/docs/extend/mcp) ระบุ `tool_timeout_sec` เริ่มต้น 60 วินาที **สำหรับ MCP บน Codex host** และบอกชัดว่า hosted plugin tools อาจมีความสามารถต่างกัน อีกทั้ง ChatGPT web ไม่อ่าน local `config.toml`. จึงห้ามเอาการตั้งค่านี้ไปอ้างว่าเพิ่มเวลา scheduled run cloud หรือแก้ “รอบ tools 30 นาที” ได้
4. [Responses API background mode](https://developers.openai.com/api/docs/guides/background) ให้แอปที่เรียก API ของตัวเองเริ่ม response แบบ async แล้ว poll ได้; เป็นคนละ execution path กับ Native ChatGPT Scheduled Task ในแชตนี้ ไม่ใช่ตัวเลือกที่ปลั๊กอิน lnwjing เปิดเพื่อยืด host turn ได้ทันที
5. [Codex hooks](https://learn.chatgpt.com/docs/hooks) มี `Stop` hook ที่สั่ง Codex local ให้ต่อเทิร์นได้ แต่เอกสารผูกกับ config/runtime ของ Codex; ไม่มีหลักฐานว่า hook นี้ใช้บังคับ ChatGPT web scheduled cloud run ได้. อย่าเพิ่ม hook เป็น “วิธีแก้” สำหรับเส้นทางปัจจุบัน

**คำตอบเรื่อง OpenAI แก้ 30 นาทีแล้วหรือยัง:** ในเอกสารทางการและ changelog ที่ตรวจวันนี้ไม่พบเพดาน 30 นาทีต่อรอบของ ChatGPT scheduled plugin, การประกาศยกเลิกเพดาน หรือ setting สำหรับขยาย host turn. จึงตอบไม่ได้ว่า “แก้แล้ว”. ภาพรอบ 2m39s ก็สั้นกว่าเพดานที่สงสัยมาก; ต้องตรวจ host run history/trace ของรอบเดียวกันก่อนโยงสาเหตุเข้ากับเพดาน 30 นาที

## Decision gate ก่อนแก้โค้ด

ตรวจรอบที่สั้นอย่างน้อยหนึ่งรอบที่มี `goal.status=active` ด้วย `runId`/เวลาเดียวกันตลอดสาย: Scheduled run history → `claim` outcome → MCP calls/errors → goal revision/checkpoint/lease → final message/host stop reason. ตัดข้อมูล token, credential, native task ID ออกจากรายงาน. ผลต้องเข้าหนึ่งกรณีต่อไปนี้ก่อนเลือก change set:

| ผลตรวจ | ความหมาย | เส้นทางแก้ |
| --- | --- | --- |
| `recurring_acquired`, งานยังมี safe next action, ไม่มี error/cutoff แต่ assistant ส่ง final | voluntary early yield | งาน 1–2: ทำ work loop ใน prompt/skill ให้สั้นและชัด พร้อมทดสอบบนโฮสต์จริง |
| `worker_busy_noop`/`already_claimed` ที่มี worker หรือ blocking job ยัง live จริง | no-op ถูกต้อง | ไม่แก้ให้แย่ง lease; ตรวจงานที่กำลังรันและการรับช่วงรอบถัดไป |
| no-op เพราะ liveness อ่านผิดทั้งที่ไม่มี worker/task | liveness bug | งาน 3: ซ่อมที่ observation/repository พร้อม clock/race test |
| tool/connector error หรือ `systemError` เกิดก่อน final | transport/host failure | เก็บ exact error และแยก retry ที่ปลอดภัย; งาน 3 เฉพาะ seam ที่พิสูจน์ได้; หากเป็น host-only ให้ส่งหลักฐานแก่ OpenAI |
| host บังคับจบที่เวลาคงที่แม้ agent ยังเรียก tool | host cutoff | ไม่อ้างว่าขยายได้จาก plugin; ใช้ durable jobs และ checkpoint เมื่อยังมีโอกาส; ถ้า cadence ชั่วโมงทำให้ค้างนาน ให้เสนอการเปลี่ยน cadence/แพลตฟอร์มเป็นการตัดสินใจแยกจากแผนนี้ |
| มี blocking job ยาวและไม่มีงานคู่ขนาน | yield ที่ skill อนุญาต | ยืนยัน `trackedTasks` เป็น `blocking_job`, task ยังรันจริง และรอบถัดไป inspect terminal result |

## Acceptance และความเสี่ยงที่ต้องรายงานตรง ๆ

- **การแก้ปัญหาหยุดเร็ว:** มี real host run ที่ claim สำเร็จ, goal active, safe work ต่อได้ แล้ว agent ทำงานต่อหลัง milestone จนถึง terminal หรือ stop condition ที่บันทึกได้; ไม่เกิด final แบบ “กำลังทำ” หลังไม่กี่นาทีโดยไม่มีเหตุ
- **ระยะเวลา:** วัด productive work จริงต่อรอบและจำนวน action/goal revision; 30+ นาทีเป็นเป้าหมายการพิสูจน์เมื่อโฮสต์เปิดให้ทำ ไม่ใช่ sleep/รอเวลาให้ครบหรือ guarantee ของปลั๊กอิน
- **ความต่อเนื่อง:** ทุก forced boundary มี checkpoint ถ้า host ให้โอกาส; ถ้าไม่ให้ โค้ดต้องกู้ด้วย lease/liveness เดิม และ scheduled task เดิมต้องปลุกต่อได้โดยไม่ทำ mutation ซ้อน
- **ขอบเขตพิสูจน์:** Vitest ตรวจ contract/state machine ได้ แต่ไม่พิสูจน์ว่า ChatGPT host จะไม่จบเองหรือไม่มีเพดาน 30 นาที; ต้องใช้ hosted run trace. หาก trace ไม่เปิด stop reason ให้คงข้อสรุปเป็น unresolved host limit
