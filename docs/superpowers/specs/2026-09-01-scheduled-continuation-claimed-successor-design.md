# Scheduled Continuation Claimed-Successor Design

Date: 2026-09-01
Target release: lnwjing 4.45.0
Branch: `dev`

## Context

A native one-time ChatGPT Scheduled Task can wake and successfully claim an active durable goal while leaving no future successor. The v4.45 incident proved the gap: the firing continuation became `claimed`, the goal stayed `active`, and a fresh successor was not reserved until the user prompted the agent again 46 minutes later.

The current prompt and bundled skill tell the agent to call `prepare_scheduled_continuation` after an `acquired` claim. That is advisory only. The repository transaction does not reserve the next generation, and the `acquired` result does not carry a required successor action. A model omission therefore becomes a liveness failure.

Native Scheduled Task creation remains host-owned. lnwjing cannot truthfully claim that a cloud task exists until the host returns a real task ID and the receipt is recorded.

## Requirements

1. A successful scheduled claim of an active goal must never leave the durable state without exactly one fresh successor reservation.
2. The firing one-time task must remain historical and must not be counted as future coverage.
3. Claim acquisition and fresh successor reservation must commit in one SQLite transaction.
4. The claim result must return the fresh successor, its host schedule request, and explicit `handoffReady: false` / `currentWakeMayReturn: false` instructions until the native receipt is confirmed.
5. Repeating a claim after an interrupted response must return the same prepared successor instead of creating duplicates.
6. A host create failure or uncertainty must remain truthful and visible; `prepared`, `create_failed`, and `create_uncertain` are not confirmed recovery coverage.
7. Goal completion must continue to cancel only a distinct still-pending successor through the existing host-receipt flow.
8. Existing collision, orphan-recovery, lease fencing, tracked-task, cancellation, and terminal-noop behavior must remain intact.
9. README and the bundled continuation skill must describe the machine-enforced handoff and the remaining native-host dependency.

## Approaches Considered

### A. Atomically reserve a fresh successor during `claim` (selected)

When the repository acquires the goal lease, it also terminalizes the firing continuation as `claimed` and inserts generation N+1 as `prepared`. The application returns the prepared successor and its `scheduleRequest` in the same `acquired` result. Repeated claims recover the same deterministic successor.

This preserves the one-time fresh-ticket model, removes the extra model-dependent `prepare` call, works with the existing receipt protocol, and can be covered deterministically in repository and application tests. The native host must still create the actual cloud task, but lnwjing can no longer silently lose the durable successor state.

### B. Re-arm the currently firing native task

This avoids nested task creation, and the current collision path already supports same-task rescheduling. It is rejected for acquired handoff because it treats a firing one-time task as future coverage, conflicts with the repository's fresh-successor contract, and depends on host behavior while the task is already running.

### C. Replace one-time tasks with recurrence

A recurring heartbeat could avoid fresh task creation on every wake. It is rejected for v4.45 because it changes the scheduling product contract, complicates cancellation and overlap semantics, and exceeds the approved scope.

## Detailed Design

### Repository transaction

`claimScheduledContinuation` will receive deterministic fresh-successor identity, due time, and request fingerprint generated by the application service. On the successful acquisition path, one SQLite transaction will:

1. acquire the new goal lease with compare-and-swap;
2. mark the firing continuation `claimed` and terminal;
3. insert exactly one generation N+1 continuation in `prepared` state;
4. return the acquired goal, historical firing continuation, and prepared successor.

The fail-safe successor delay is two minutes. The existing collision path can keep moving a confirmed pending native task by two minutes if the new wake collides with the still-active worker.

If a previous response was interrupted after the firing continuation became `claimed`, a repeated claim will locate the deterministic generation N+1 row. A fresh `prepared` reservation, or a truthfully failed create with no native ID, returns `successor_required` with the same row and a reusable `scheduleRequest`. A `prepared` row without a host receipt, `create_uncertain`, or any already-recorded native ID returns `successor_required` with a reconciliation reason and no blind-create request. A stale `create_failed` row without a native ID may be refreshed to a new +2-minute due time only after the failed host create is truthful. A confirmed scheduled successor returns `already_claimed`. A legacy claimed row with no successor is repaired by inserting the deterministic recovery row, even when the previous lease was released.

### Application and MCP contract

The `acquired` result will include:

- the lease token and generation;
- the historical firing continuation;
- the fresh prepared successor;
- the successor `scheduleRequest`;
- `handoffReady: false`;
- `currentWakeMayReturn: false`;
- `nextRequiredAction: create_native_task_and_record_receipt_before_current_wake_returns`.

The native prompt and MCP tool description will say that `acquired` already reserved the successor. The worker must create and record the returned task rather than calling `prepare_scheduled_continuation` again.

### Failure handling

- Host create success: record `created` with the real native task ID, host-reported due time, and `runsOn: cloud`; require readback status `scheduled`.
- Host create failure or uncertainty: record the exact failure state and continue retrying while the current lease is valid. Do not report recovery coverage or yield with an active goal.
- Replay safety: never create blindly from `prepared`, `create_uncertain`, or a row that already has a native task ID; reconcile exact host metadata first. Only a truthfully failed create with no native ID may receive a fresh +2 retry request.
- Goal finishes before successor fires: finish the goal first, delete the exact pending native successor when instructed, record the deletion receipt, and require terminal cancellation state.
- Transaction failure: claim acquisition and successor insertion roll back together; no partial acquired-without-successor database state is committed.

## Test Strategy

1. Storage regression: the first successful claim produces a historical `claimed` row plus exactly one fresh `prepared` generation.
2. Storage idempotency: repeating the claim returns the same successor and never inserts another generation.
3. Application regression: `acquired` returns the successor schedule request and non-return handoff flags.
4. Receipt flow: the fresh successor transitions from `prepared` to confirmed `scheduled` with an immutable native task ID.
5. Finish flow: a pending acquired successor is cancelled through the existing exact-host receipt protocol.
6. Contract tests: tool descriptions, bundled skill, README, and generated prompt agree on the acquired-successor behavior.
7. Release verification: focused continuation suites, full workspace tests, acceptance, packaging, release gate, docs catalog, diff check, Windows packaging, and packaged provenance verification.

Repository tests establish the lnwjing state machine and contract. A real two-wake ChatGPT host run remains the release-level proof for native scheduling behavior; source tests alone must not be reported as host E2E proof.
